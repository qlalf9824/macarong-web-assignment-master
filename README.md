## 먼저 화면 구조를 정리했습니다

예약 목록이 루트(`/`)에 있어서 경로만 보고는 어떤 화면인지 알 수 없었습니다. 상세는 `/reservations/[id]`인데 목록만 `/`에 있는 것도 어색해서, 목록을 `/reservations`로 옮기고 `next.config.mjs`에 `/` → `/reservations` 리다이렉트를 뒀습니다.

파일도 목록 화면 하나에 예약 카드 UI까지 들어 있었고, 상세 화면은 `page.tsx` 안에 `InfoRow`와 `DecisionPopup`이 인라인으로 정의돼 있었습니다. 라우트마다 `_components/`를 만들어 UI 조각을 꺼내고 페이지 파일에는 페이지 로직만 남겼습니다.

## reservation.ts 한 파일에 너무 많은 역할이 뭉쳐 있었습니다

코드를 읽으면서 가장 먼저 눈에 걸린 건 `lib/reservations.ts` 였습니다. API 응답 타입, 화면에서 쓰는 타입, 라벨 상수, 날짜·금액 포맷 함수, fetch 호출, URL 조립, localStorage 접근이 한 파일에 모두 들어 있었습니다.

파일 이름은 `reservations` 인데 실제로는 예약과 관련된 모든 것이 담겨 있어서, 화면에서 포맷 함수 하나만 필요해도 fetch와 localStorage 코드까지 함께 딸려 오는 구조였습니다.

같은 파일을 서버와 클라이언트가 함께 쓰다 보니 `apiUrl()` 안에 "서버에서 실행되면 절대 URL을 만든다"는 분기가 들어가 있었고, 그 때문에 SSR prefetch 과정에서 서버 컴포넌트가 자기 자신의 Route Handler를 HTTP로 다시 호출하고 있었습니다.

이 왕복을 바로 없앨 수는 없었습니다. 데이터 소스인 목 생성기가 `app/api/_lib/mock.ts` 에 있어 Route Handler에서만 접근할 수 있었기 때문입니다. 서버 컴포넌트가 데이터를 직접 가져오려면 서버 컴포넌트와 Route Handler가 함께 사용할 수 있는 계층이 필요했고, 그 계층을 만들려면 먼저 한 파일에 섞여 있던 포맷·모델·API 호출을 갈라야 했습니다.

결국 왕복 제거가 목표가 아니라, 역할를 구분하는 작업을 하기로 했습니다.

그래서 작업 순서도 자연스럽게 정해졌습니다.

**포맷 분리(#3) → 모델 분리(#4) → service 계층(#5) → 상세 서버 컴포넌트화(#6) → 나머지 분해와 서버 왕복 제거(#7)**

PR 순서는 단순히 작업하기 편한 순서가 아니라, 앞 단계가 있어야 다음 작업을 진행할 수 있는 의존 순서로 잡았습니다.

### 1. 실행 환경을 기준으로 레이어를 나눴습니다

`lib/` 아래 구조는 다음과 같이 정리했습니다.

| 위치           | 역할                        |
| -------------- | --------------------------- |
| `lib/service/` | 서버 전용 데이터 접근       |
| `lib/api/`     | 브라우저 전용 `/api/*` 호출 |
| `lib/storage/` | localStorage 접근           |
| `lib/models/`  | 공용 타입과 데이터 변환     |
| `lib/utils/`   | 공용 포맷 함수              |

기능보다 어디에서 실행되는 코드인지를 기준으로 나눴습니다.

`lib/service/*`에는 `import "server-only"`를 넣어 클라이언트 컴포넌트가 잘못 import하면 빌드 단계에서 바로 실패하도록 했습니다. 실제로 클라이언트 컴포넌트에서 service를 import해 빌드가 깨지는 것도 확인했습니다.

클라이언트용 `apiUrl()`도 상대 경로만 반환하도록 바꿨습니다. 서버에서 실수로 클라이언트용 fetch 함수를 사용하면 조용히 동작하지 않고 바로 문제가 드러나도록 하기 위해서였습니다.

### 2. 화면에서 API 응답 가공을 없앴습니다

기존 상세 페이지에서는 API 응답을 그대로 받아 화면에서 직접 가공하고 있었습니다.
이를 `lib/models/`에서 다음과 같이 분리했습니다.

- 서버 응답 타입 `Api*`
- 화면에서 사용하는 `Reservation`, `ReservationDetail`
- 변환 함수 `toReservation`, `toReservationDetail`

화면에 흩어져 있던 가공 로직을 변환 함수로 옮기고, 화면에서는 `data.payment.methodLabel`처럼 이미 가공된 값을 읽기만 하도록 바꿨습니다.

변환 함수는 서버와 클라이언트 양쪽에서 사용할 수 있도록 순수 함수로 유지했습니다. localStorage의 확정/불가 상태처럼 브라우저에서만 알 수 있는 값은 모델 안에서 처리하지 않고 호출하는 쪽에서 병합했습니다.

### 3. 서버에서 할 수 있는 일은 서버에서 처리했습니다

service 계층을 만든 뒤에는 서버가 Route Handler를 거치지 않고 데이터를 직접 가져오도록 변경했습니다.

**예약 상세**는 `useEffect` 기반 클라이언트 fetch를 제거하고 서버 컴포넌트에서 service를 직접 호출했습니다. 로딩과 없는 데이터 처리도 직접 상태를 관리하지 않고 `loading.tsx`, `notFound()`, `not-found.tsx` 같은 프레임워크 규약에 맡겼습니다.

뒤로가기나 확정/불가 처리처럼 실제 상호작용이 필요한 부분만 클라이언트 컴포넌트로 남겼습니다.

**예약 목록**의 SSR prefetch 역시 service를 직접 호출하도록 변경했습니다. 기존에는 목록 1회와 고객 정보 10회로 초기 렌더마다 HTTP 요청이 11번 발생했지만, 서버 내부 함수 호출로 옮기면서 해당 HTTP 요청을 모두 제거했습니다.

즉, BFF를 없앤 것이 아니라 클라이언트가 필요한 API 경계로만 좁혔습니다. 서버에서는 Route Handler를 다시 거치지 않고 안쪽 service를 직접 사용하도록 했습니다.

### 4. localStorage 상태는 hydration을 기준으로 처리했습니다

확정/불가 상태와 취소 예약 숨기기 설정은 localStorage에만 있어 서버가 알 수 없습니다. 이를 첫 렌더에서 바로 읽으면 서버 HTML과 클라이언트 첫 렌더가 달라져 hydration 문제가 발생할 수 있습니다.

그래서 두 상태 모두 같은 규칙을 적용했습니다.

1. 서버와 동일한 기본값으로 시작
2. 마운트 후 localStorage 값 반영
3. 저장은 effect가 아니라 사용자 액션 시점에 처리

특히 읽기 effect와 쓰기 effect를 동시에 두면 마운트 시 기존 localStorage 값이 초기 상태로 다시 덮어써질 수 있었습니다. 그래서 저장은 토글 핸들러처럼 실제 사용자 액션이 발생한 시점에만 하도록 옮겼습니다.

### 5. 구조를 정리하면서 기존 버그도 발견했습니다

데이터 흐름이 단순해지면서 기존 기능 문제도 더 잘 보였습니다.

- `getNextPageParam`이 항상 `undefined`를 반환해 무한 스크롤이 실제로 동작하지 않고 있었습니다.
- React Query의 `queryKey`에 `per_page`가 없어 페이지 크기가 달라도 같은 캐시를 사용하고 있었습니다. SSR prefetch와 클라이언트 queryKey가 어긋나면 hydration된 데이터도 재사용되지 않기 때문에 함께 수정했습니다.
- 로딩과 없는 데이터에 대한 화면은 있었지만 예외 처리 화면이 없어 루트 `error.tsx`를 추가했습니다.
- 목 데이터의 약 1%가 존재하지 않는 `customerId`를 가지고 있었고, 기존 코드에서는 한 건의 실패로 `Promise.all` 전체가 reject되어 목록 전체가 실패했습니다. service에서 해당 예약만 제외하도록 처리했습니다.

버그를 먼저 하나씩 고치기보다 구조를 먼저 정리한 이유도 여기에 있습니다. 데이터 흐름을 정리한 뒤에야 증상만 고치는 것이 아니라, 왜 문제가 발생했는지를 기준으로 수정할 수 있었습니다.

## PR은 리뷰어가 편하게 볼 수 있도록 나눴습니다

PR을 나누면서 가장 중요하게 생각한 것은 리뷰하는 사람이 변경 이유와 코드를 쉽게 따라갈 수 있는가 였습니다.

한 번에 큰 변경을 올리기보다 한 PR에서 하나의 변경 의도만 확인할 수 있도록 나눴습니다. 파일을 옮기는 작업과 실제 동작을 바꾸는 작업도 최대한 분리해, 구조 변경과 로직 변경을 동시에 따라가지 않아도 되도록 했습니다.

각 PR 본문에는 왜 이 작업이 필요한지 / 무엇이 바뀌었는지 / 다음 작업에서 무엇을 할지를 적었습니다. 현재 PR만 보더라도 변경 이유를 이해할 수 있고, 이후 작업이 어떤 방향으로 이어지는지도 알 수 있도록 하기 위해서였습니다.

작업 단위 자체보다 리뷰어가 변경의 이유와 영향을 편하게 확인할 수 있는지를 기준으로 PR을 구성했습니다.
